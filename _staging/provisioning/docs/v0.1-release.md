# v0.1 release scope and success criteria

Status: planned implementation baseline, grounded in ADR Campus’s Decisions Office YAML artifacts. Binding validation, parent-context input, and concrete provider operations remain to be specified.

## Release outcome

An operator can load the Decisions Office definition from public Git, supply deployment bindings and parent context, and review the resulting plan in a Blazor single-page app. The engine provisions owned resources selected by those bindings, validates inherited capabilities, and produces usable deployment configuration. See [the input model](input-model.md).

v0.1 is a working end-to-end release with a real Redis-backed draft workspace and a valid parent context. The exact Redis resource and access operations must be agreed before implementation; selecting Redis does not by itself specify them. Simulated or in-memory-only runs are development milestones, not sufficient for release.

The first release is intended for a trusted operator in a controlled environment. It does not include a publicly exposed, multi-user provisioning service.

## In scope

### Definition loading

- Load one institution from a public Git repository, with a selected branch, tag, or commit and a definition location.
- Resolve and record the exact commit used, so a moving branch cannot silently change an already reviewed plan.
- Validate the supported definition version and return actionable errors for missing or invalid input.
- Parse the declarative institution YAML and separate bindings YAML. Preserve stable IDs and validate cross-references, institution identity, ownership, and binding compatibility.
- Record the definition commit, bindings provenance and effective configuration identity, and parent-context identity in the plan. Operator overrides must not modify the institution definition.
- Keep fetching a source separate from interpreting it. Private Git credentials can be added later.

The supplied definition is plain YAML; reading it requires no repository build or code execution. The runtime currently has no YAML loader. The provisioner must explicitly handle the artifact’s IDs, ownership, and dependencies, including fields beyond `IInstitutionTemplate`. Required parent dependencies must not be ignored.

### Standalone engine

- Expose .NET APIs for loading, validating, planning, and executing without a UI dependency or interactive prompts.
- Represent missing configuration and validation failures as structured results.
- Combine institution requirements, deployment bindings, and parent context into a plan with stable resource identifiers, ownership, resolved provider kinds, dependencies, effective non-secret settings, and provenance.
- Distinguish owned provisioning actions from inherited capability checks. An unresolved parent capability blocks dependent work; it never becomes an implicit request to create parent infrastructure.
- Apply explicit overrides before producing the final reviewable plan. Changed inputs require a new plan.
- Report progress and a final per-resource outcome through host-independent contracts.
- Provide cooperative cancellation and record completed work when execution stops.

### Blazor operator experience

- A single-page workflow for source selection, plan review, provider configuration, execution progress, and results.
- Show owned resources, inherited resources/capabilities, binding choices, and missing inputs separately. Present provider settings only after a deployment binding selects that technology.
- Generate required resource credentials by default, with optional explicit overrides.
- Require a deliberate provisioning action after review; loading or planning alone makes no infrastructure changes.
- Show existing, created, failed, and blocked resources distinctly. Support retrying an incomplete run.
- Provide a runtime configuration output, with secret material handled separately from ordinary plans and logs.

### Initial deployment and provider boundary

The supplied Decisions bindings select a Workbench with Redis backing for the owned draft workspace. The decision record is parent-owned; `IArchive`, `ILibrary`, `IPostOffice`, and `IRegistrar` must resolve from the parent context. Their validation must not create or modify parent resources.

The supplied in-memory fallback must be shown as non-durable and applied only under an explicit deployment policy. A failed Redis connection must not silently switch a reviewed persistent deployment to in-memory storage.

MongoDB databases, S3 buckets, and Keycloak clients remain planned adapter targets for deployments that actually select them. They are not requirements of the Decisions Office definition or mandatory v0.1 creation actions. Provisioning those parent services requires a separately scoped parent definition and bindings.

- Use operator-supplied connections and administrative credentials for existing provider services.
- Create and verify resources in dependency order.
- Inspect existing resources before creating them. Reuse only when compatible; report conflicts instead of overwriting unrelated configuration.
- Fail visibly on unsupported resource types or settings. Never omit an unsupported requirement and report the institution as complete.
- Document and test the selected Redis/Workbench configuration and the parent capability integration. Specify what is allocated, which existing service is used, and how access is verified. Broader provider compatibility is not a release requirement.

Installing provider servers, including Redis, MongoDB, S3 services, or Keycloak, and recursively provisioning parent institutions are outside this release.

### State, credentials, and outputs

- Persist enough run state to resume after restarting the app, including plan identity, resource outcomes, and references to required secrets.
- Use cryptographically secure generation for required secrets. Reuse stored values on retry; do not silently rotate them.
- Keep administrative credentials and generated secrets out of source control, ordinary plan serialization, progress messages, and logs.
- Select and document a protected secret-storage mechanism before implementing credential persistence. Ordinary run-state files must not contain plaintext credentials.
- Associate state with the institution, resolved source commit, effective bindings, parent context, and target environment so unrelated runs cannot accidentally share completion records.
- Export configuration in a form agreed with the actual institution. Report incomplete outputs clearly after partial failure.
- Prevent concurrent execution against the same run state in the supported deployment mode.

## Explicitly out of scope

- Private Git authentication.
- A CLI product, hosted provisioning API, scheduler, or CI-specific integrations. The engine must remain callable without Blazor.
- Fully unattended provider discovery or acquisition of administrative credentials.
- Multi-user access control, approvals, organization tenancy, or a public service deployment.
- Destructive teardown, automatic rollback, resource migration, or modifying conflicting existing resources.
- Continuous drift reconciliation, credential rotation, and upgrades of already provisioned institutions.
- Arbitrary provider plugins, arbitrary repository code execution, and exhaustive provider compatibility.
- Campus composition editing or redesigning the runtime's institution model.

## Success criteria

Every criterion below must pass before tagging v0.1.

| ID | Acceptance scenario | Required evidence |
| --- | --- | --- |
| SC-01 | Load the supported institution from public Git using a branch or tag; also load it by commit. | Both resolve to an explicit commit recorded in the plan. A later branch change does not alter that plan. |
| SC-02 | Plan Decisions with its deployment bindings and parent context. | The draft workspace is owned; the decision record is inherited; all four parent contracts are checked. Missing bindings, unsupported ownership, or unresolved dependencies block dependent execution with useful errors. No parent creation actions are inferred. |
| SC-03 | Change deployment defaults, bindings, or parent context and review again. | The new plan reflects those inputs without modifying the institution definition; the previous review cannot authorize different settings. |
| SC-04 | Execute the Redis-backed Decisions deployment with an existing valid parent. | The owned workspace is configured and verified according to the agreed binding operations. Parent capabilities resolve, and parent-owned infrastructure is unchanged. An in-memory-only run does not satisfy this criterion. |
| SC-05 | Provision without supplying resource-level secrets, then repeat with explicit secret overrides. | Generated credentials work in the first run; the supplied overrides work in the second. Neither appears in ordinary plans or logs. |
| SC-06 | Run the same completed plan again. | No duplicate resources or unintended credential changes occur; existing compatible resources are identified. |
| SC-07 | Interrupt or fail execution after some resources succeed, restart the host, and resume. | Completed work and secret references survive; retry finishes remaining work without rotating credentials or duplicating resources. |
| SC-08 | Encounter an incompatible existing resource or unavailable provider. | The run reports the affected resource and dependent resources accurately, preserves unrelated infrastructure, and never reports overall success. |
| SC-09 | Execute through a non-UI test host. | The same plan and engine execute without Blazor services, UI state, or interactive prompts. |
| SC-10 | Use the exported configuration with Decisions under its parent. | An integration check demonstrates durable draft staging and usable inherited Archive, Library, Post Office, and Registrar capabilities, without duplicating their infrastructure. |
| SC-11 | Cancel a run or attempt a concurrent run against the same state. | Cancellation preserves completed outcomes; overlapping execution is rejected or serialized. |
| SC-12 | Build and validate a clean checkout. | Documented commands and CI pass unit tests; a recorded integration run covers the supported provider configurations. |

## Decisions required before live implementation

1. A supported YAML contract/versioning policy and validation rules for the supplied institution and bindings artifacts; descriptor version is not assumed to be a schema version.
2. Parent-context representation and how each required contract is resolved and verified.
3. Concrete Workbench/Redis allocation, naming, access, ownership, compatibility checks, and explicit fallback policy.
4. Supported Redis/Workbench versions/endpoints and minimum administrative permissions, including which resource credentials need generation.
5. Protected secret storage, state location/locking, and configuration output consumable by the mounted Decisions institution.

Resolve these at the milestone gates using the supplied definition and bindings. Test doubles may model a parent context, but a simulated parent does not replace the live integration evidence required for release.
